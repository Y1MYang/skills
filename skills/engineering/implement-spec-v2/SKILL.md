You have been provided a spec. This spec should have tickets associated with it, describing how to implement the spec.

The goal is a PR which implements the entire spec on a single branch, plus a test suite derived **independently** from the implementation.

The tickets form a **task graph**. Schedule independently verifiable **work units**, combining small tickets or splitting a large ticket where this reduces elapsed time while preserving every ticket and requirement in the mapping. A unit enters the **frontier** when its implementation dependencies are integrated and its required critical-contract checkpoints have current passing evidence. Unrelated units remain parallel.

Communication to and from subagents should be sparse. Communicate primarily through **context pointers**: to the spec, tickets, exploration notes, the architecture doc, and previous commits. Don't duplicate information already available via pointers.

**Implementer subagents** should be run in the background where possible. Keep normal concurrency while resources fit the space admission policy below.

## Subagent model selection

At the start of each invocation, before step 1 or any subagent dispatch, collect the user's explicit model selections for the roles below. Ask for any selections not already supplied with this invocation, presenting all six categories together and the current runtime's available model choices when known. Offer both category-wide selections and individual role selections; leave unanswered selections unset.

| Category | Roles |
| --- | --- |
| 1 | Exploration |
| 2 | Architect |
| 3 | Test implementer, Implementer |
| 4 | Coverage audit, Standards reviewer, Spec reviewer |
| 5 | Merger, Checkpoint, Fixer |
| 6 | Expert |

Accept category numbers, role names, or both in one reply. A category selection applies to every role in that category; an individual role selection overrides the category selection for that role. The same model may be selected for multiple categories or roles.

Honor explicit selections supplied for this invocation and ask only for missing or ambiguous selections. Wait for the user's answer until all eleven roles have an explicit model. A partial reply, no reply, or elapsed time leaves the remaining roles unassigned. Never fill them from the main conversation's model, runtime defaults, or a previous invocation. The user may explicitly choose the main conversation's model for any role.

Check that the selected models are supported by the current runtime and that its dispatch tool can select them. If a model is unavailable or explicit selection cannot be honored, explain the limitation and ask for a supported choice or a workflow change; do not silently substitute a model. Once all eleven assignments are resolved, show the role-to-model mapping and proceed without another confirmation.

Retain this mapping for the invocation and save it in the shared notes directory once that directory exists. Every instance, retry, replacement, and nested delegation must use its role's selected model. A user-requested change updates future dispatches for the affected roles.

Pass the selected model explicitly through the dispatch tool's model parameter or supported equivalent; a model name written only in the task prompt does not select the model. When model overrides require a fresh or bounded context instead of a full-history fork, use that mode and provide the task's context pointers, preserving the test side's independent inputs.

For `/test-review` in steps 8-10, a **coverage-audit subagent** coordinates using the Coverage audit model: the Spec reviewer handles contract semantics and whole-spec coverage; the Standards reviewer handles test executability and applicable test standards. Failure-scoped review may use the coordinator's lightweight triage instead of both reviewers. Final `/code-review` in step 10 retains its Standards and Spec reviewers. Pass the resolved mapping and explicitly select the corresponding models for every nested dispatch, retry, and replacement. All review file work follows the steps 6-10 delegation rules.

## On-demand Expert help

The **Expert** model is selected at startup, but the role is dispatched **only on a qualified help request**, never as part of the normal workflow. Any working subagent, including nested reviewers, or the main conversation may request help after one evidence-backed investigation leaves a specific technical blocker unresolved with no known executable way to proceed.

Resolve the Expert protocol pointer relative to this SKILL.md into a location accessible to the subagents. Pass that resolved pointer, the Expert model assignment, and this help rule to every subagent, including nested dispatches. A requester reports a **needs-help** event with its blocker and investigation evidence; the main conversation verifies the request from that report and dispatches a fresh Expert. Nested requests reach the main conversation through their coordinating subagent.

Subagents requesting or handling Expert help read [references/expert.md](references/expert.md) for role-specific triggers, the request and handoff protocol, read-only diagnosis, one-shot termination, and escalation to the user, and include the applicable protocol requirements in their reports to the main conversation. Give the dispatched Expert that reference and only the inputs its task is allowed to see. In steps 6-10, the main conversation delegates any needed reference lookup as file work and relies on the resulting report. This protocol applies in every phase, including within a checkpoint or fixer round; consulting an Expert preserves the existing ownership, input boundaries, and round budgets.

## Resource lifecycle

For watch setup, a delivery boundary, or a resource alert, read [references/resource-audit.md](references/resource-audit.md). The helper requires Git and Python 3 standard libraries; resolve it relative to this skill rather than using a machine-specific path. If a required capability is unavailable, report the limitation and retain the affected resources.

- Track only resources created for this invocation. Keep the ledger, generated test outputs, and compact evidence outside the source repository; keep required source fixtures under the project's existing rules.
- Initialize an invocation-owned notes root, register the PR branch's first remote publication, bind its native REST PR response, and seal the final handoff under the resource protocol. A later explicit `cleanup-spec-v2 <PR number>` invocation can then locate this delivery from a new conversation and present its complete cleanup list for confirmation.
- Every test attempt leaves a validated compact record. Keep the necessary raw scene of an unresolved failure; after resolution and evidence validation, release regenerable data. Final acceptance also leaves only a compact record, without a retained final archive.
- Release resources at their delivery boundary and include a handling receipt in the delivery report. Prefer revision pointers and necessary diffs over complete source-tree copies; replacement agents inherit the original resources and round counts.
- Reserve measured or conservatively estimated growth through the helper before new allocations or material command growth, accounting for other admitted tasks on the destination filesystem. Preserve normal concurrency when space suffices. Under pressure, release eligible resources and temporarily admit fewer new tasks; preserve running tests and builds. If even one task cannot fit, report the deficit instead of retrying allocations unchanged.
- Release requires verified saved work, readable evidence, and confirmed inactivity. Preserve ambiguous, dirty, or still-active resources with a reason in the ledger. Cleanup is file work: in steps 6-10 it remains with the existing resource owners, merger, checkpoint, or fixer; the main conversation retains its dispatch-only boundary.
- A 30-minute script watch checks this invocation's metadata and destination free space. Owners handle alerts; the existing merger checks receipts at delivery boundaries and handles escalation. The watch creates no agent role or model assignment, and its ability to report does not guarantee that the platform wakes a model.

## Steps

1. Read the spec and tickets. Read enough to understand the task graph.

2. Dispatch an **exploration subagent** to conduct the exploration required by the tickets - relevant codebase files or external documentation. This step is **mandatory**: the architecture phase depends on it. Extract the existing acceptance behavior, observable evidence, timing boundaries, threshold sources, and fixture/environment assumptions into a separate test-safe summary, citing authoritative requirements and immutable historical evidence. Inventory the project's runner boundaries, isolation and termination capabilities, and comparable execution-budget evidence under the execution protocol. Distinguish requirements from observed behavior and unresolved assumptions; keep implementation details in the implementation-side notes. The exploration subagent must be able to save files - it initializes the invocation-owned notes root and its nested ledger with `init --notes-root` before saving markdown notes outside the repo, accessible by later subagents within their input boundaries. Follow [references/resources.md](references/resources.md); configure destination capacity and start the invocation watch under [references/resource-audit.md](references/resource-audit.md), reporting its CLI/session identifier and output channel. Pass the resolved protocols, helper path, notes root, ledger path, and watch delivery pointer alongside the existing context pointers to subsequent subagents.

3. Create the PR branch in a new invocation-owned PR worktree using the resource helper. Use `publish-branch` for its first remote publication, create a draft PR, then use `bind-pr` with a fresh native REST PR response. Pass this registered worktree's ID and path to mergers and fixers so their commands can use it throughout integration. The PR should be marked as 'closing' the spec issue and tickets.

4. Dispatch an **architect subagent**. Its inputs are the spec, the tickets, and the exploration notes; it may do small supplementary exploration, but the notes are the primary source. Pass the resolved [architecture decisions reference](references/architecture-decisions.md) and require the architect to read it before designing: justify abstractions and compare alternatives where the decision warrants it. It produces an **architecture doc** for the new code introduced by the spec, saved in the same out-of-repo notes directory. The doc must satisfy this **content contract** before it can be released:
   - module boundaries and responsibilities
   - concrete public API signatures and types
   - core data structures
   - error semantics
   - observability seams: where tests enter the system, where mocks/fixtures are injected; a shared acceptance-contract table under the resolved test-review reference, recording required behavior, reliable evidence, timing start/end events, threshold sources, and fixture/environment assumptions; an execution contract under the execution protocol, defining worker/case/phase boundaries, declared progress, finite budgets and sources, isolation, termination scope, and the execution gate
   - integration seams: which existing modules the spec touches, which existing public surfaces the new code hangs on, compatibility/migration constraints
   - delivery plan under the architecture decisions reference: work units, test-contract batches, and a finite set of critical-contract checkpoints with explicit prerequisite and release edges, acceptance scopes, concurrency and execution budgets; retain complete ticket/requirement traceability

5. Review the architecture doc yourself against the content contract and the [architecture decisions reference](references/architecture-decisions.md); return material design or evidence gaps to the architect before approval. Check that the graph including checkpoint prerequisites and release edges is acyclic, and approve and register the finite acceptance plan under the execution protocol before formal runs. Approve a separate test-safe public architecture/acceptance package, excluding implementation observations and details; unresolved business semantics are not silently turned into test requirements. On approval, release **both sides at once** (test side and the available implementation frontier). If the design introduces highly irreversible surfaces - public APIs, data models, or other cross-service interfaces - do not pause for sign-off; instead record them in an **irreversibility report** in the notes directory, to be surfaced to the user in the final PR report (step 12).

**Delegation rules for the test and implement phases (steps 6-10): the main conversation does no file work.** Every file query (reading code, docs, notes, diffs, test output, or resource files) and every file modification (writing code, tests, merges, fixes, worktrees) is performed by a subagent. The main conversation **dispatches subagents** and queries their **status and deliverables** on completion, failure, timeout, Expert requests, or a delivered structured **execution-alert** under the execution protocol. During acceptance execution, use bounded status queries through the existing runner/owner to obtain per-worker progress and pending alerts; each wait must return control within a finite interval suitable for user updates. These queries inspect delivered metadata, never files or raw logs. It may also dispatch from a delivered structured **resource-alert**, following [references/resource-audit.md](references/resource-audit.md), without opening the ledger or resource files. On failure or timeout, query the subagent's handoff and re-dispatch rather than taking over its file work.

6. Dispatch the **test side** by the approved **test-contract batches**. Group tests that share a public contract and can be reviewed with a known dependency closure; prioritize batches needed by the earliest critical-contract checkpoints. Use one Test implementer unless independent batch work justifies parallel authors within the approved concurrency and capacity limits. Each author uses an isolated worktree and branch; a merger integrates deliveries into the dedicated **test branch**. One test owner produces each shared helper; other authors reuse its pinned version. Tests derive only from the spec and approved test-safe package. Preserve author worktrees through coverage and checkpoint repairs, then release them after final integration and review fixes. Deliver fixed batch revisions plus a **ticket/requirement -> work unit -> batch -> observable test** mapping, including shared helper, fixture, configuration and public-contract dependencies. Record changes to acceptance behavior or budgets with their requirement sources. Test authors and all formal repairs remain implementation-blind.

7. Dispatch the **implementer side**: one **implementer subagent** per ready work unit, each in its own worktree and branch, within the approved concurrency and capacity limits. Implementers MUST read the architecture doc; public seams are bound by it, while unit-internal details are their own call. They stay blind to formal tests; throwaway checks never enter the delivered test suite. A **merger subagent** integrates each completed unit into the PR branch, verifies the delivery and its unit/ticket mapping, preserves compact evidence, and releases its idle worktree. Its report includes handling receipts and outstanding obligations under the resource audit protocol. Recompute the frontier after integration or checkpoint results: merging a prerequisite alone cannot release a unit whose critical contract is still unqualified. Start unrelated ready units while tests, reviews and checkpoints proceed. Implementation branches continue from the PR branch without the formal tests; scratch union candidates are never their development base.

8. As each batch is ready, dispatch a fresh **coverage-audit subagent** to invoke the resolved `/test-review` with **batch** scope on its explicit requirements, fixed test base/head, contracts and dependency closure. Use the selected reviewer models and a clean test-safe context. Passing both axes and the complete declared batch scope gives **local qualification**, usable only for that scope's checkpoints. Send findings to the Test implementer, then review the repaired **delta** and affected closure; reuse only qualified, unaffected evidence with matching inputs. Shared helper, fixture, configuration, timing-policy or public-contract changes invalidate every affected batch. Once all required batches are accounted for, perform **full** whole-spec reconciliation, carrying forward valid batch evidence and reviewing gaps and cross-batch interactions. Only this complete, qualified result blesses the full test suite. The test branch remains separate from the PR branch until step 10.

9. Run each planned **critical-contract checkpoint** when its implementation prerequisites are integrated and all tests for its declared scope have local qualification. Dispatch the existing **Checkpoint** role to create an immutable, clean, committed **scratch union candidate** from fixed implementation, test and contract revisions. Verify the bound execution gate, run the checkpoint scope as formal acceptance under its registered key and budget, and report qualified behavior evidence before releasing its dependent units. A test batch does not automatically create another checkpoint. Reuse the owned scratch through immediate repair/verification rounds, and reuse its execution proof only while all bound inputs still match. A passed checkpoint with changed dependent inputs uses the execution protocol's continuation path, retaining its original history and budget; a later new scratch binding may require a new execution proof. Unresolved failures follow repair/recovery instead. Apply classification before repairs: a Fixer repairs implementation on the PR branch; the blind Test implementer repairs tests, followed by affected-scope review. Preserve compact results and necessary failure scenes outside scratch, then release it at delivery when no repair/verification obligation remains and its users are idle. This is temporary integration; formal tests enter no implementation development base.

10. Once all work units are integrated and whole-spec test coverage is blessed, a merger integrates the test branch into the PR branch and freezes a clean committed candidate. In parallel, have the run owner verify its execution gate and run **complete formal acceptance** under the registered final key, and dispatch a **Coverage audit** subagent to run read-only `/code-review` with the selected reviewer models on the **same frozen SHA**. Reviewers use a separate read-only snapshot; neither branch changes while these checks run. Collect both outcomes before coordinated repairs. A **single Fixer** diagnoses and repairs implementation; test findings go through fresh implementation-blind test-review with neutral evidence and then the Test implementer. A merger integrates reviewed test repairs. Each new candidate needs complete acceptance and review of its changes and affected scope; unaffected qualified review evidence may carry forward with explicit revision links. Pure implementation changes do not repeat test-review. Keep the existing final-chain repair, frontier and recovery accounting under the execution protocol, including the 3-round repair budget and continuation confirmation after every 10 unconsumed frontier rounds; checkpoint budgets do not cap or replenish it. Ready-for-review requires both final review and one qualified full-scope run aligned with the delivered SHA.

11. Have the responsible subagents reconcile the resource ledger, handling receipts, and capacity reservations, then release remaining temporary worktrees, including the test side's and the invocation-owned PR working copy now that integration and review fixes are complete. Preserve the delivered PR branch and commits; use that branch as the PR worktree's release target. Every registered resource must be released or retained with an explicit reason and recovery pointer. Stop the invocation watch and confirm its completion before sealing. On failure, cancellation, or timeout, preserve active commands and necessary failure state, then hand off the original resources and watch status under the recovery rules rather than creating duplicate environments.

12. Push the final delivered PR branch to its registered destination and mark the PR as ready for review only after final execution qualification under the execution protocol. An unexplained first hang leaves acceptance **unverified** and the PR **draft**, even if a later complete attempt passes; report the remaining diagnosis and evidence gap. After saving the final invocation notes, have a responsible subagent fetch a fresh native REST PR response and seal the handoff with the selected qualified final run and full approved acceptance-scope/source file. That run must match the delivered head; historical or partial success is insufficient. An unverified handoff requires the fresh PR response to establish `draft: true`. Report the PR, resource release results, retained paths and reasons, and `cleanup-spec-v2 <PR number>` for cleanup after merge. If step 5 produced an **irreversibility report**, it leads the report: each highly irreversible public API, data model, or interface the architecture introduced, with its final signature and a one-line rationale, so the user can review the decisions now that they are implemented.

## Conflict and ownership rules

- **Architecture doc vs work unit**: public seams follow the approved architecture; unit-internal details follow the mapped tickets and implementer. Record adjudicated conflicts and preserve ticket/requirement traceability when changing unit boundaries.
- **Stale evidence vs broken contract**: stale checkpoint evidence or a changed batch in its dependency closure blocks new releases through that checkpoint while affected work already in flight may continue. A proven need to change a public contract pauses only affected in-flight units at a safe boundary with saved work and evidence. Record the corrected contract and affected closure, repair and requalify through the existing owners, then resume. Unrelated units continue. Replacements inherit the original resources and counters; plan changes do not create fresh checkpoint budgets.
- **Test failure classification**: Checkpoint/Fixer reports each round's hypothesis, distinguishing check, new evidence, classification, and responsible owner before repair. Classify implementation defects, test/contract defects, fixture/environment problems, missing spec decisions, or unresolved causes; an unclassified failure is not presumed to be an implementation defect. On the first timeout of each unresolved failure, distinguish the measured business event, evidence wait, harness limit, and environment, then report a test-safe failure package to the main conversation for fresh Coverage audit dispatch. Invoke **failure**-scoped test-review using only neutral events/times/fixture/environment facts. It audits test semantics and budgets; implementation diagnosis stays with Checkpoint/Fixer. A scoped review does not repeat whole-spec review or renew blessing for changed tests.
- **Formal test repairs and contract changes**: Test implementers remain implementation-blind and own every formal test repair. Test-review is read-only; it cannot change business SLAs. The main conversation adjudicates from authoritative requirements, recording the reason and before/after contract for justified test or budget changes; ask the user only for a genuine unresolved business choice. Re-review changed tests and affected dependencies; shared helper, fixture, timing-policy, or business-contract changes widen the scope. Retain valid findings for unchanged inputs rather than repeating full review each round.
- **Stopping and budgets**: Stop implementation optimization when an attempt produces no new evidence supporting the next repair; return to distinguishing diagnosis and contract adjudication. A proven test/contract contradiction stops affected repairs immediately. Continue unrelated work and preserve advancing commands. The registered checkpoint keys, scopes, execution limits and fixed repair/recovery histories survive batches, rechecks, changed agents and failures. Checkpoint and final chains remain separate; neither inherits the other's case history or fresh budgets. A frontier continuation confirmation resets only its batch counter. At exhaustion, report evidence and remaining decisions to the main conversation rather than restarting the same repair loop.
- **Execution alerts and recovery**: The run owner supplies neutral worker/case/phase facts and a durable handoff; the main conversation routes diagnosis and adjudicates from that report. Follow the execution protocol for bounded capture, owned termination and at most one conditional automatic recovery of the same unresolved failure. Evidence-backed repair verification uses its separate ledger route within the original checkpoint/fixer limit, including revalidation after review repairs; it does not replenish recovery credit. Contract corrections require authoritative adjudication and independent test-review evidence. Formal qualification requires an exclusively held, immutable committed clean candidate and verified source/gate at completion. Keep the original failure, acceptance contracts, resources and round counts through every retry or replacement.

## Discipline

- Context pointers, not duplication.
- In steps 6-10, preserve the dispatch-only boundary above, including when a structured resource alert triggers owner or merger work.
- Implementers stay **blind to spec tests** while writing code. This is what keeps the tests an independent oracle. Checkpoint fixes happen after their code is written, so the independence of authoring is preserved.
