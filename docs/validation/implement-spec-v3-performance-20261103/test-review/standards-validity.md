## Review correction and risk

1. **Withdrawn finding — do not require E06's killed controller to return final JSON.** Version 1 proposed asserting exit 2 and a structured error after lines 501–504. Runtime-contract line 35 defines `claim.controller` as the runner; neither that contract nor performance-contract §3 requires it to differ from the outer execute process. A compliant implementation may therefore be terminated by this injection before it can emit a response. The proposed assertion would introduce an unsupported process-architecture restriction. E06 correctly tests recovery after owned-controller death. Separately, shared helper lines 203–214 already requires initial execute exit 2, `ok:false`, no marker/receipt and one pending preparation after dirty formal preflight; E08's later matching receipt adoption verifies the useful bound prefix. Performance-contract line 98 expressly permits specific runner/evidence errors instead of `execution-incomplete`. This is valid representative initial no-receipt error coverage. It does not claim all possible failure causes are covered, and no E06 strengthening is required on this basis.

2. **Risk — E07's waiting-target reservation has no explicit allowance for the worst combination of its control waits.** Lines 530, 539, 540, 542, 545 and 550 each use the inherited 15-second CLI hang cap (`test_cycle.py:265–275`); their ceilings sum to the entire 90-second runner reservation before startup and local observation work. These are upper caps, not expected durations, so their sum does **not** establish an observed or likely failure on this tiny local fixture. This is nonblocking absent actual boundary pressure. If this test times out, distinguish target-deadline expiry from an absent ownership behavior using neutral command intervals and the actual failing predicate before changing any allowance. Do not infer a regression or arbitrarily raise a budget from the arithmetic.

No missing business decision was identified for the reviewed assertions. Missing additional contract cases are for coverage reconciliation, not evidence that an existing assertion is invalid.

## Timing and evidence limits

- The ordinary **5-second runner reservation** begins at runner preflight and ends at execution deadline, with at most the contract's **5 additional seconds** for termination/collection. It is an explicit controlled workload allowance, not a benchmark acceptance ratio. Target work is a tiny local Python fixture; formal cases add Git and snapshots.
- The inherited **15-second CLI cap** spans each `subprocess.run` command including process startup, CLI audits, nested execution where applicable, output collection and shutdown. The standalone runner fixture has a separate **20-second command cap** covering its 5-second reservation, cleanup and wrapper margin. Neither proves business speed. Finite per-call caps and a finite list of steps bound these tests; no progress event renews a deadline.
- The waiting helper's **10-second acknowledgement wait** is an evidence wait: `t0` is the explicit monotonic deadline immediately before `accept`; `t1` is receipt of target byte `R`. The remaining time is shared by socket acceptance and receive, so the second wait does not restart the allowance. Initial helper creation/preflight occurs outside that measurement but inside the runner's **90-second** deadline. The source comment's harness wording does not change the acknowledgement's evidence-wait role.
- After the test sends release, **15 seconds** bounds collection of the helper result; failure cleanup waits **10 seconds**, then kills the test-created outer helper and waits **5 seconds**. These are harness/cleanup limits, not target performance expectations. Native interruption uses a **5000 ms** handle-exit evidence wait. No fixed sleeps or claimed heartbeat-based business progress are used.
