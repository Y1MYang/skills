# implement-spec-v3 反馈循环与执行成本审查

日期：2026-11-03。审查对象是工作区当前 v3 技能、引用协议及 Python 运行工具，不是某个提交之间的 diff。本次只审查并调研，没有修改技能或运行工具。外部方法及来源见[研究记录](../research/2026-11-03-agentic-tdd-workflows.md)。

## 结论与证据边界

当前设计将一个行为例子的测试反馈、多个职责交接、证据持久化和共享状态协调绑定得很紧。存在可确认的重复工作与全局同步点。首先应缩小每个反馈循环所需的协调成本，而不是把开发退回一次实现整个 ticket。

以下是静态控制流与协议审查，未测量真实任务各阶段的墙钟时间；因此没有提速倍数，也不能认定某一项已经被证明占总时间最多。旧验证报告提供其已覆盖场景的正确性证据，不能作为本轮吞吐量基准。

应用的 pstack 原则：修复根因、先减后加、解释测量数字、测试行为而非实现。

## 主要发现

### 1. 微步骤接口缺少低协调成本的连续执行路径

[runtime-ledger.md](../../skills/engineering/implement-spec-v3/references/runtime-ledger.md) L75–85 定义一个新行为的最简成功路径：

```text
open → prepare(probe) → run → record → judge(valid-red)
     → implement → prepare(green) → run → record → close
```

无重构、无重试且 Green 命令同时覆盖受影响回归时，需要七个 `apply` 和两次测试执行。`cycle.py` L1148–1149 的 CLI 一次接收一个事件；Test author、Runner、Implementer、Integrator 则分别持有测试、执行、产品和共享状态权限。

持久化步骤不等于模型回合：现有规则并未要求每个事件单独唤醒一个代理。问题是缺少把机械步骤连续执行的标准入口，调度者容易把每个状态变更当成一次任务派发。写 JSON、转述结果、检查状态和重新加载上下文会进入测试反馈路径。

建议先保留全部语义事件及真实 Red 判断，令常驻角色与本地驱动连续执行机械步骤；每次仍只新增一个行为测试，在该行为 Green 后选择下一个。可以一次授权一条流连续完成多个顺序循环，但不能把多项未知行为测试预写成一个批次，也不能在执行前伪造后续成功记录。

### 2. 状态查询与每次更新都重新审计全部历史

[cycle.py](../../skills/engineering/implement-spec-v3/scripts/cycle.py) L1154、1174：包括 `inspect` 在内的操作先取得全局状态锁，再执行 `audit_history`。L939–952 遍历全部历史事件和 attempt；L477–481 重读并哈希每份历史 stdout/stderr。L987–989 随后在保存时计算并写入整份状态。

所以历史越长，每个小操作读取的旧材料越多，频繁查询同样支付这份成本。多个流的状态操作争用同一把锁；竞争调用立即返回 `busy`，需要调用者协调重试。这个锁不覆盖外部测试运行，不能据此声称所有测试均串行。

建议先减少不必要查询和同一事务的重复计算。进一步采用增量审计、已验证历史前缀或独立只读状态视图，需要先定义证据不可变性的保证与失效规则；只用文件时间戳缓存、或直接删掉审计，会改变现有完整性保证。恢复、显式完整校验及正式交付仍须检验真实证据。

### 3. 独立工作副本的并行设计没有贯通到开发证据

[architecture-and-flow.md](../../skills/engineering/implement-spec-v3/references/architecture-and-flow.md) L29 要求独立流使用各自工作副本；但 `cycle.py` L143–145 强制每个 example 的 snapshot root 等于同一个 run workspace，L460–461 又要求执行 receipt 的 cwd 与准备时的 root 一致。

因此各流不能直接将自己工作副本中的 Red/Green 执行作为该运行认可的开发证据：需要在共同 workspace 运行或先搬运相应版本，增加协调与阶段性交付。这不妨碍共同 workspace 中互不重叠路径的测试并行，但限制了文档所描述的独立副本方案。

建议为开发证据显式绑定 flow/workcopy 身份，正式验收才绑定共同集成候选。此项涉及快照、归属、恢复和证据资格协议，属于运行契约修订，不能仅改路径校验。

### 4. 局部补录升级为所有流的同步屏障

`cycle.py` L812–813、L887–888 及 [runtime-ledger.md](../../skills/engineering/implement-spec-v3/references/runtime-ledger.md) L55、67 要求全部 flow inactive、attempt settled 才允许 `extend/include`。一条流补充行为或遗漏依赖，就要等待无关流也到达空闲边界。

这比 [architecture-and-flow.md](../../skills/engineering/implement-spec-v3/references/architecture-and-flow.md) L39 的“暂停受影响消费者，无关流继续”更保守。建议按受影响依赖闭包决定暂停范围，仍由 Integrator 原子校验合并后的完整计划，并正确撤销受影响证据。这同样需要协议与恢复测试，不能无条件取消屏障。

### 5. 正式校验内部有重复快照读取

`cycle.py` L706–724：`check_qualification` 调用 `capture(snapshot)`，`prepare_formal` 紧接着再捕获一次；L752、761 的 `check_formal` 也有同类重复。资格判断只需比较测试/契约，当前 capture 仍读取产品文件。

在相同已固定输入、明确写入归属的一次事务中，可以研究复用捕获结果或只捕获所需组。Runner 执行前后、实际编辑前后及不同候选之间的采样有不同作用，不能跨这些边界直接复用。尚未测量此项相对代理等待的成本，优先级低于连续执行路径。

## 不应误判为新增缺陷的已接受约束

- 十个职责需要显式选模型是用户的明确选择；职责不等于十个常驻或每轮重建的代理。`dispatch-and-isolation.md` L7 已区分二者，L37 允许未污染的 Test author 跨例持久化。
- 每轮一个新行为例子是已接受的 TDD 粒度。它不要求每轮重新创建上下文，也不要求每个账本事件单独一次对话。
- 完整双轴测试审查已经移到关键契约和最终验收，不是每个例子都做。产品单独变化也不必重新审查未变的测试。
- 开发阶段要求受影响回归，Green 可以同时覆盖回归；规则没有要求每个 Green 都跑完整验收。
- 最终同一候选的完整验收、双轴代码审查、主代理只调度及测试侧盲隔离均为已接受边界。优化不应悄悄取消它们。
- 局部诊断预算已允许依据新证据自主追加。本轮所见的成本不能再归因于旧的固定 `2/2` 停止规则。

## 建议的两个演进方向

**先做保持隔离规则的执行简化。** 主代理调度开发流；未污染的测试作者、实现者及执行/记账责任持续工作；每个新行为仍按 Red → Green → Refactor 顺序推进。机械命令由工具连续完成，语义判断、争议与契约变化交给对应角色。批量汇报不等于事后补造证据。精简完成后再评估每流工作副本和增量审计。

**若需要更大幅度调整，试验独立验收外环＋开发者 TDD 内环。** 外环从 spec 盲写公开行为验收测试；内环让实现代理使用小步开发测试持续红—绿—重构；外环在行为切片或关键契约完成时验证。开发测试也必须从行为契约推导预期，而不是复制实现输出。此方案明确改变“所有测试盲写、同一套测试兼任开发与验收”的 v3 选择；内环测试不能冒充独立验收证据。它是有依据的设计候选，不是本次已实施变更。

## 提速应如何验证

用相同起点、spec、模型选择、质量门槛和执行环境，对比当前流程与候选简化流程，覆盖普通新增行为、缺陷修复、共享契约变化。分别记录模型等待与生成、调度交接、账本/快照、环境准备、目标测试、正式审查及返工耗时；并行阶段应按关键路径归因，不能把并发时间相加冒充墙钟。

同时检查独立验收结果、现有回归、测试判据质量、重放恢复和失败历史。报告多次运行的范围与中位数，不以事件数减少或测试命令耗时替代端到端收益。当前尚未运行这一对比，因此建议是优先级判断，不是已验证的性能承诺。
