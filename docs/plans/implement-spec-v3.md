## 现状：需要改变的是循环和信息流

v2 已允许拆分或合并 ticket，按可验证工作单元调度，并设置关键契约检查点。它并非规定每次必须写完整个 ticket。

偏离小步 TDD 的核心是：架构批准后同时放行测试与实现；检查点在相关实现完成后验收，没有强制当前行为先出现有效 Red 再开始实现。另一个需要评估的现有机制是实现者开发时看不到正式测试；它影响反馈方式，本身并不排除小步先测后写。

来源：[v2 的调度、隔离与检查点](../../skills/engineering/implement-spec-v2/SKILL.md)、[架构与工作单元](../../skills/engineering/implement-spec-v2/references/architecture-decisions.md)。

## Q1 已确认：保留判据独立，采用单向隔离

必须保留的目标是：正确答案从权威需求及已明确的公开契约得出，不能从待测实现、实现运行结果或内部算法反推。测试作者、测试审查者和测试修复者的输入也需要维持这一边界。

这里的独立性约束针对承担独立验收判据的测试。下表 C 是曾考虑的替代方案；其开发者自写测试只能提供开发反馈，不能自动取得独立验收资格。

另一方向的信息流——实现者能否读取测试——影响的是测试对实现者的保密程度，以及开发反馈速度。它与正确答案的来源不能混为一谈。

双盲改为单盲并非 TDD 的逻辑必要条件。若 runner 在实现开始前运行当前测试、确认有效 Red，再逐轮反馈，双盲同样可以先测后写；它需要额外协调，也限制实现者直接利用测试定位问题。

| 方案及选择 | 测试侧看实现 | 实现者看正式测试 | 逐行为循环 | 主要代价 |
| --- | --- | --- | --- | --- |
| A：单向隔离，已接受 | 否 | 可读已独立编写的当前测试 | 测试侧写测试 → 确认 Red → 实现者运行测试并写最小实现 → Green → Refactor | 实现者更易针对有限用例凑通过，需要覆盖与独立审查 |
| B：双向隔离，本次未选择 | 否 | 否 | 测试侧写测试 → runner 确认 Red → 实现者依据公开契约和允许反馈修改 → runner 验证 | 每轮多次交接，反馈粒度需要设计 |
| C：开发者 TDD 加独立验收，本次未选择 | 独立验收侧不看 | 可读自写测试，独立验收另定 | 开发者执行 TDD，独立验收检验规格 | 两套测试的重复、差异与维护成本 |

选择 A 的理由是同一套独立测试能直接驱动开发，而不是 B 无法实现 TDD。B 与 C 作为取舍记录保留，不再是 v3 当前设计的开放分支。

具体例子：需求规定满 100 元免运费，否则运费 10 元。测试作者从需求写出 `99 → 10`、`100 → 0`。在 A 中，实现者可读这些测试，但不能修改期望值；在 B 中，实现者仍知道业务规则，只是不知道隐藏用例。两者都可能遗漏其他边界，也都可能得到错误实现；隐藏测试本身不能替代覆盖质量。若实现者质疑测试，应提交需求层面的争议，由未接触实现的测试侧裁定和修复。

## 单向隔离下的架构草案

以下流程采用已确认的 Q1—Q13。每一步都保留需求、公开契约、测试与产品版本的对应关系。

1. 梳理完整规格、ticket、行为清单和依赖。先确定外部边界、关键跨模块契约与集成约束；当前行为开始前细化所需公开接口，内部结构随 TDD 演进。
2. 选取一个新的行为例子作为当前切片。ticket 是需求追踪容器，行为切片是 TDD 循环单位；一个 ticket 可以经历多轮。
3. 未接触实现的测试作者只为当前例子编写一个主要测试，记录需求依据、契约及测试版本，完成轻量判据核对。一个例子可有共同描述同一可观察结果的多个断言；一个测试函数不能夹带多个尚未分别验证的行为。全局覆盖计划可以先有，完整测试实现不提前批量生成。
4. 在已知基线上运行当前测试，确认它因目标行为缺失或错误而失败。缺失的目标公开接口可以构成有效失败；无关编译错误、环境故障和错误 fixture 不能冒充有效 Red。首次即 Green 时走既有能力验证路径，不声称新增了 Red → Green 历史。
5. 实现者只完成当前例子所需的实现，运行当前测试及受影响回归，得到开发 Green。
6. Green 后按需重构，保持公开行为不变，再次运行受影响测试。实现重构由实现侧执行，测试及共享测试 helper 的重构仍由实现盲测试侧执行；相同规则的已验证例子可由测试侧合并为参数化测试。无需重构也可完成本轮，重构不成为提前开发下个例子的入口。
7. 记录本轮测试、契约、实现和运行证据的版本关系，再推进下一行为。每条开发流内部串行，独立开发流可并行；隔离各流写入目标，集成后验证受影响行为。被标记为关键契约消费者的工作，必须等待相应检查点放行。
8. 在关键契约检查点完成相应范围的双轴 test-review 与正式运行。最后核对全规格覆盖、交互行为与审查结果，在同一最终候选版本上执行完整验收与代码审查，交付覆盖整个 spec 的一个 PR；最终证据必须与交付 head 对齐。

一个已知关键契约内部的前置例子也按普通 Green 继续推进，不需要等待整个契约审查。例如 `99 → 收费` 通过后可以编写 `100 → 免费`；检查点等待这些前置例子完成，再放行使用完整运费契约的消费者。每个检查点明确验收范围、前置行为和被阻塞消费者，检查点本身不能依赖被它阻塞的实现。

核心过程可以写为：

```text
需求与公开契约 → 当前行为的独立测试 → 有效 Red
                                             ↓
                                     最小实现 → Green
                                                  ↓
                                   按需 Refactor → 回归 Green
                                                  ↓
                                         下一行为 / 最终验收
```

## 必须讨论清楚的异常路径

- **已有能力**：当前测试一开始就通过时，记录已存在的能力与证据，不能故意破坏实现制造 Red；必要时检查测试是否真的检验了需求。
- **测试错误或规格不明**：区分实现缺陷、测试缺陷、环境问题与未决业务语义；实现者不能为通过测试而修改独立判据。
- **契约变化**：变更公开接口或业务语义时，先明确权威依据和影响范围；不能把实现现状自动提升为新需求。协调者将实现诊断改写成“公开契约”，也不能使它成为独立的需求依据。
- **证据过期**：共享测试 helper、fixture、配置或公开契约变化会影响先前结论；受影响的运行结果需要重跑，受影响的测试判据资格需要重新审查，不能只检查当前测试。未受影响的证据可以在明确版本关系后复用。
- **输入污染**：新 worktree 不等于隔离。含实现的会话历史、git diff、提交说明、调试栈和探索笔记都可能污染测试侧。接触实现的作者不能继续以独立测试作者身份工作；污染后的产物须由干净上下文重新判定或重写，不能自动沿用独立资格。现有工具能遵循输入规则，但不能因此声称建立了物理访问沙箱。
- **重试和恢复**：原始失败、版本与修复历史应保留。不能通过换 agent、改切片名或重建目录抹掉未解决的问题。
- **并行合并**：两个开发流各自 Green，不等于合并后 Green；合并结果需要验证。

这些约束来自独立测试与有效证据的目标。公开契约修订采用统一路径：记录公开差异与权威依据 → 确定受影响行为、消费者和测试 → 固定新契约版本 → 由独立测试侧修订 → 刷新受影响证据。保持业务语义的技术细化由架构职责处理；真正缺失的业务或兼容性选择才交用户。契约变更暂停受影响消费者在安全边界继续依赖该契约，不回滚所有已完成工作，不阻塞无关开发流。

## 开发反馈与正式验收

分别记录两类证据，复用同一套独立测试：

- 开发反馈记录有意义的 Red → Green，以及后续重构仍然保持行为。首次就 Green 的行为单列为“既有能力验证”，保留检查测试有效性的结论，不声称拥有 Red → Green 历史。
- 正式验收证明最终交付版本满足完整范围，测试判据经过独立审查，运行证据有效。

v2 的正式执行绑定干净、提交且冻结的候选，并有有限检查点预算。每轮预期 Red 若机械套入该失败/修复流程，会把正常开发消耗当作验收异常。v3 将有效 Red 记录为正常开发结果，将实现缺陷、测试缺陷、环境问题、缺失业务决定和未知原因分别处理；保留完整正式验收。分阶段审查与关键依赖放行的取舍见 [ADR-0002](../adr/0002-stage-test-qualification.md)。

来源：[测试审查的隔离与资格](../../skills/engineering/test-review/SKILL.md)、[验收判据](../../skills/engineering/test-review/references/acceptance-contract.md)、[v2 执行协议](../../skills/engineering/implement-spec-v2/references/test-execution.md)。Q5 已确定完整双轴审查放在关键契约检查点和最终验收；变更后按受影响范围刷新资格，不能把旧资格当作当前资格。

测试审查判断测试是否忠于需求、判据是否可靠；有效 Red 判断这一次实际失败是否由目标行为缺失或错误导致，两者不能互相代替。轻量核对至少说明需求来源、公开观察边界、独立预期值和失败条件；运行侧另外核对实际失败原因，保留对应版本和证据。

测试侧接收的运行材料限定为公开输入输出、事件、时间、断言结果、fixture 与环境事实及证据标识。实现代码、私有堆栈、局部变量和实现诊断留在实现/运行侧；需先由测试审查之外的材料所有者形成中性摘要，再交给测试侧。公开结果可用于发现问题，不能自动成为正确答案。

## pstack 原则如何约束设计

| 原则 | 对本方案的影响 |
| --- | --- |
| redesign-from-first-principles | 从逐行为先测后写重新设计调度与信息流，而不是在 v2 的大批次完成后补一句执行 TDD |
| sequence-verifiable-units | 当前行为验证通过后才放行依赖它的下一行为；整个 ticket 不作为默认循环粒度 |
| test-behavior-not-implementation | 预期值来自需求，经公开边界观察；行为变化能使测试失败，内部重构能保持测试通过 |
| build-the-lever | 本轮产出可复用的[草案评估规程](implement-spec-v3-review.md)；实施时再按实际需要建立最小运行证据检查工具，避免先造工作流框架 |
| separate-before-serializing-shared-state | 独立流并行时先隔离写入目标；真实共享对象采用单一写入者或结构上的串行阶段，不能只靠口头约定防止并发写入 |

| 问题 | 已确认选择 | 主要取舍 |
| --- | --- | --- |
| Q4 循环粒度 | 每轮一个新的行为例子、一个主要失败测试；相同规则的用例可在重构阶段合并为参数化测试 | 更短反馈周期，增加测试侧与实现侧的交接次数；避免一次编写完整行为的全部用例 |

| Q7 并行策略 | 独立开发流并行，每条行为依赖链内部串行 | 缩短总耗时；必须隔离写入目标并验证合并结果 |
| Q8 最终交付 | 默认一个覆盖整个 spec 的 PR，同一最终版本完成全量验收与代码审查 | 保留完整规格交付目标；行为切片是内部循环而非默认拆分 PR 的单位 |
| Q9 v2 接管兼容 | 首版支持 v3 自身中断恢复，不新增未完成 v2 任务的接管兼容；保留现有 v2 技能 | 控制首版范围；不能把旧运行状态直接视为 v3 有效状态 |

## 角色、模型与主代理边界

职责是权限边界，不代表每个切片都创建一套常驻代理。实现职责兼顾产品重构与实现修复；运行职责兼顾开发反馈、检查点及最终执行；集成职责兼顾合并和资源文件操作。

| 职责 | 核心产物与边界 |
| --- | --- |
| Exploration | 代码库事实与依赖；另外产生可交给测试侧的中性材料 |
| Architect | 外部边界、公开契约、依赖和变更影响；从需求给出设计依据，不把实现细节转译为测试要求 |
| Test author | 保持实现盲，编写当前例子的独立测试，进行轻量自检，负责测试修复与重构 |
| Implementer | 根据当前测试进行最小实现、产品重构和实现修复；不修改独立测试 |
| Runner | 有效 Red 判断、版本绑定的执行结果、有限等待与中性事实；运行前接收已由测试侧记录的需求与预期失败条件 |
| Integrator | 合并、集成验证协调、资源与状态文件管理；共享集成目标单一写入 |
| Coverage audit | 保持实现盲，协调正式测试资格与全规格覆盖核对 |
| Spec reviewer | 测试审查时保持实现盲；最终代码审查使用另一个新上下文实例 |
| Standards reviewer | 测试审查时保持实现盲；最终代码审查使用另一个新上下文实例 |
| Expert | 按阻塞问题临时委派；实现侧与测试侧的 Expert 上下文严格区分，测试侧保持实现盲 |

每次调用在委派前集中收集以上职责的显式模型选择，允许用户一条回复为多个或全部职责指定同一模型。未回答的职责保持未指定；不以超时、主会话模型、运行时默认或上次选择补齐。检查当前运行时支持情况，真实派发参数必须匹配选择；不可用时说明限制并请求可支持的选择或流程调整，不静默替换。每个重试、替换和嵌套审查沿用本次对应职责的选择。

测试、实现、检查点、最终审查和修复期间，主代理只分配任务、消费结构化交付报告、协调契约及向用户沟通。代码、文档、diff、原始日志、状态和资源文件的读取与修改全部交给子代理；失败和资源告警也不例外。主代理可以根据报告作出技术协调决定，但不能通过接管文件工作绕过此边界。

独立测试上下文可以跨同一开发流的切片持续使用，只要输入边界未被污染；需要替换时从明确的测试侧材料恢复。实现者可读取当前和已交付的独立测试，但不能反向向测试作者提供实现方案。测试侧只得到允许的材料清单和指针，不继承实现会话历史；运行与集成产物在回传前经过边界检查。信息隔离是可核查的流程约束，不声称提供物理访问沙箱。

## 执行、证据与恢复的最小工具

复用 v2 的有界运行、资源所有权、证据绑定和恢复连续性等语义；不整体搬用其执行状态机。事实核查发现：

- [execution_supervisor.py](../../skills/engineering/implement-spec-v2/scripts/execution_supervisor.py) 明确要求 Linux `/proc`，不能直接满足本机 Windows。
- [resources.py](../../skills/engineering/implement-spec-v2/scripts/resources.py) 的非正式 `--test` 不消耗正式验收预算，但非零退出仍被当作待解决失败；不带执行契约的普通路径使用无超时的等待。现有接口不具备“正常预期 Red”的完整语义。
- [acceptance_plan.py](../../skills/engineering/implement-spec-v2/scripts/acceptance_plan.py) 的固定检查点计划不能直接充当逐例、渐进契约的开发状态。v2 的资源状态与 cleanup 身份也不能直接冒充 v3 状态。

实施时建立小型可移植工具，优先覆盖本机 Windows，并以隔离的平台适配实现其他受支持环境；不要求先将 v2 全部移植。工具只负责可以机械核验的事项：

1. **记录与校验**：保存运行标识、开发流/切片、需求和契约版本、测试及依赖快照、产品基线与结果版本、执行命令、结果、日志指针、所有者和资源。每个阶段绑定不可变版本或内容摘要，不用一个可变工作目录代表历史 Red 与 Green。
2. **推进门槛**：新行为实现前存在轻量核对及有效 Red 的判定记录；既有能力走单独出口；下一切片之前当前切片及受影响回归通过。检查点放行另需有效测试资格和对应固定版本执行。工具核验记录与版本关系，不能仅凭退出码或自填状态证明需求语义正确。
3. **有界执行**：每条运行声明有限时限、进度观察和停止范围；时限来自项目配置、已知运行数据或有说明的估计，与业务 SLA 分开。等待定期返回控制权；终止只作用于本次拥有的进程和资源。原始日志留在运行侧，给测试侧提供中性摘要。
4. **失败与恢复**：有效 Red 是正常结果，不消费正式验收失败修复额度，但仍消耗本次声明的执行时间和资源。其他失败先分类，下一次修复必须有新的诊断依据；达到已声明的时间/尝试边界或无法形成下一项可区分的检查时，保留现场并报告。换代理、改切片名、重开运行或改计划不得重置同一未解决问题的历史与额度。
5. **并行与资源**：各流独立写入证据和工作副本；集成分支与共享索引有单一写入者。并发由依赖、执行环境容量与已声明的运行预算共同约束，不按 ticket 数直接铺开。恢复先核对现存进程、工作副本、版本及所有权，再继续原运行，避免重复启动。结束释放无待办的临时资源，保留交付分支、必要证据及有明确原因的故障现场。

运行前根据实际项目明确有限预算、正式检查点的范围与放行关系；渐进契约变化保留修订与受影响证据失效记录，不新建身份来获得额外预算。不存在当前可凭空指定、又适用于所有项目的统一秒数或修复轮数。

正式验收在干净、已提交、执行期间冻结的候选上进行。完整验收与代码双轴审查针对同一候选；修复后重新对齐最终证据。只有完整范围的有效执行与审查共同支持交付 head，才标记 PR 可评审；中断、挂起或未解释失败不以之后某次通过自动抹除。

首版只恢复 v3 自身记录，原 v2 及其接管、清理技能保持原有行为。v3 资源不能交给只认识 v2 状态的 cleanup 工具；合并后额外清理不因本轮方案自动发生。
