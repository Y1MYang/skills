# implement-spec-v3 草案评估规程

这是供评审代理复用的评估规程，不是 implement-spec-v3 的可执行实现。每当方案或用户选择变化时，用它重新检查[方案草案](implement-spec-v3.md)。

## 输入与边界

读取当前草案、用户本轮明确选择、草案引用的必要源文档。区分用户要求、现有 v2 机制、候选推荐和未决决定。只评估文档，不修改文件，不运行待设计的技能，不提交代码、不操作外部应用。

仅需要事实核实时查阅源文档；引用具体路径和段落。不把候选推荐当作用户同意，不把缺失的实施细节自动解释成已经承诺的能力。

## 可复现的检查步骤

1. 列出已确认的不变量和仍未决定的分支。核对草案是否把信息来源、读取权限、审查资格、产品运行结果混在一起。
2. 对当前选定方案运行下表场景；若仍有开放候选，再逐个比较。从文字中推出下一步、责任边界和受影响证据。没有明确答案就记录“未决”，不要自行补齐后宣称通过。
3. 检查一个包含多个行为的 ticket：是否会先写完整套测试或完整实现？当前行为尚未有效验证时，是否允许实现依赖它的后续行为？
4. 检查当前草案的引用是否可定位，是否声称已完成实际运行验证。文档推演不能证明未来技能执行可靠。
5. 返回有依据的问题和依赖关系；明确哪些需要用户决策，哪些只是事实错误或可直接修正的表述。

## 场景

| 场景 | 必须检查的结论 |
| --- | --- |
| 测试作者收到了带实现 diff 的旧会话 | 新 worktree 是否被误认为恢复独立性；污染后是否继续拥有独立测试修复资格 |
| 当前测试第一次运行已经 Green | 是否伪造 Red；是否区分已有能力与测试判据不足 |
| 测试运行因无关环境错误退出 | 是否把它算作目标行为的有效 Red 并启动实现 |
| 共享 helper 修复导致旧测试含义改变 | 是否仍沿用旧资格或旧 Green；是否记录受影响范围 |
| 实现者认为需求规定的阈值不合理 | 是否直接改期望值或预算；裁决依据是否来自权威需求 |
| 公开契约需要变更 | 是否把现有实现反推为需求；是否重新审视受影响测试与证据 |
| 预期 Red 反复耗尽正式验收修复预算 | 是否区分正常开发反馈与正式失败；是否反过来取消所有停止条件 |
| 两个并行开发流各自 Green，合并后失败 | 是否把两个通过结果相加当成合并后证据 |
| 当前行为卡住，换了 agent 和切片名称 | 是否丢失原始失败与恢复历史，是否凭改名取得无限重试 |
| 关键契约还有一个前置例子未实现 | 下一例是否被整个契约审查反向阻塞；消费者是否过早开工 |
| 实现者将多个正式测试整理成参数化测试 | 是否借重构绕过测试侧所有权；是否重新检查依赖和判据 |
| 某个职责尚无显式模型选择 | 是否静默继承主模型、运行时默认或旧运行选择 |
| 执行失败后主代理直接读取原始日志修复 | 是否绕过只调度边界，是否将诊断泄露给独立测试侧 |
| Windows 运行依赖 Linux /proc 的监督器 | 是否把协议语义可复用误写成现有代码可直接运行 |

## 输出格式与完成标准

报告包含：发现（严重程度、文档位置、具体反例）、未决选择（前置依赖）、无发现时的覆盖范围说明。

完成标准是每个场景都得到“已有明确规则 / 明确未决 / 存在矛盾”中的一个有依据结论，并且没有把用户尚未选择的方案记录为已接受。通过只代表草案没有在这些场景中暴露矛盾，不代表技能已完成或运行通过。
